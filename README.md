# Арена: маяк и монеты — многопользовательская веб-игра в реальном времени

Лабораторная работа №4 (СПП). Игра на чистом JavaScript: сервер Node.js + WebSocket, клиент
HTML/CSS/Canvas без единого фреймворка (никаких React/Vue/Express — только стандартные модули
Node.js и минимальная библиотека `ws` для протокола WebSocket).

Игроки бегают по клеточной арене, собирают монеты (+1 очко) и борются за общий **Маяк** (+5 очков).
Все действия мгновенно синхронизируются у всех участников, а конфликты одновременных действий
разрешает сервер.

## Соответствие требованиям

| Требование | Реализация |
|---|---|
| 1. Мгновенная синхронизация через WebSockets | Каждое изменение порождает событие, которое сервер немедленно рассылает всем клиентам (`server.js`, функция `broadcast`). Клиент рисует новые координаты с интерполяцией, поэтому движение плавное. |
| 2. Только JavaScript, без фреймворков | Сервер — `node:http` + `ws`; клиент — ванильный JS (`public/game.js`), Canvas 2D, DOM API. Нет React/Vue/Angular/Express/Socket.IO. |
| 3. Сохранение данных между запусками | Всё состояние (игроки, очки, монеты, маяк, номер события) пишется в `data/game.json` атомарно (временный файл + `rename`), с дебаунсом и при завершении процесса. При старте состояние загружается. |
| Доп. 1. Конкурентный доступ | Оптимистичные блокировки через `version` у монет, маяка и игрока + идемпотентность операций по `opId` + единая точка сериализации на сервере. Проигравший получает сообщение `conflict` с актуальным состоянием элемента. |
| Доп. 2. Потеря соединения | Клиент кэширует состояние в `localStorage` и продолжает его показывать; при переподключении отправляет `resume` с токеном и номером последнего события — сервер досылает пропущенные события (`replay`) или полный снапшот (`state`). Очередь неподтверждённых операций отправляется повторно. |
| Доп. 3. Развёртывание | Локальный запуск: `npm start`, игра доступна по ссылке <http://localhost:3000> (инструкции для публичного хостинга — в разделе «Развёртывание»). |

## Запуск

```bash
npm install
npm start
```

Откройте <http://localhost:3000> в двух окнах/браузерах (или на двух устройствах в одной сети:
`http://<ip-машины>:3000`) и играйте одновременно.

Тесты:

```bash
npm test
```

## Управление

| Клавиши | Действие |
|---|---|
| `W A S D` / стрелки | движение по клеткам (одна клетка — один шаг) |
| `E` / `Пробел` | взять монету под собой или захватить маяк |

Правила: на одной клетке может стоять только один игрок, **кроме клетки маяка** — там
разрешается стоять нескольким игрокам, поэтому одновременный захват маяка разрешается
конфликтом. Монета даёт +1, захват маяка — +5. Взятая монета возрождается в случайной
свободной клетке.

## Структура проекта

```
server.js              HTTP-сервер статики + WebSocket-сервер, heartbeat, персистентность
src/game.js            игровая логика (чистая, без транспорта): правила, конфликты, сериализация
public/index.html      разметка интерфейса
public/style.css       оформление
public/game.js         клиент: рендер Canvas, ввод, WebSocket с реконнектом, кэш localStorage
test/game.test.js      unit-тесты игровой логики (node:test)
test/integration.test.js  интеграционные тесты через реальные WebSocket-соединения
data/game.json         состояние игры (создаётся автоматически, в git не хранится)
```

Игровая логика вынесена в `src/game.js` без зависимостей от транспорта: сервер только
преобразует сообщения WebSocket в вызовы `game.move/take/capture` и рассылает события.
Благодаря этому правила и конфликты покрыты быстрыми unit-тестами.

## Протокол WebSocket (JSON)

Клиент → сервер:

| Сообщение | Назначение |
|---|---|
| `{t:'join', name, token?}` | вход в игру (с токеном — восстановление известного игрока) |
| `{t:'resume', token, lastSeq}` | переподключение: «у меня есть состояние до события `lastSeq`» |
| `{t:'move', opId, fx, fy, dx, dy}` | шаг из клетки (`fx,fy`) в направлении (`dx,dy`) |
| `{t:'take', opId, coinId, baseVersion}` | взять монету |
| `{t:'capture', opId, baseVersion}` | захватить маяк |
| `{t:'sync'}` | запросить полное состояние |
| `{t:'ping', ts}` | измерение задержки |

Сервер → клиент:

| Сообщение | Назначение |
|---|---|
| `{t:'welcome', token, youId, state}` | ответ на `join`, полное состояние |
| `{t:'replay', youId, seq, you, events:[…]}` | досылка пропущенных событий после `resume` |
| `{t:'state', youId, state}` | полный снапшот (если историю событий досылать нельзя) |
| `{t:'ev', seq, k, …}` | событие мира: `player`, `moved`, `coinTaken`, `coinSpawned`, `beacon` |
| `{t:'conflict', opId, kind, reason, …}` | отказ операции с причиной и актуальным состоянием |
| `{t:'pong', ts}` | ответ на `ping` |
| `{t:'rejoin'}` | токен неизвестен (например, база состояния очищена) |

Все изменяющие сообщения несут `opId`; все события — монотонный `seq`.

## Разрешение конфликтов (доп. 1)

Сервер — единственный источник истины и обрабатывает сообщения строго последовательно, поэтому
гонки данных невозможны «физически». Поверх этого работает оптимистичный контроль версий:

1. **Версия элемента.** У каждого изменяемого элемента есть `version`: у монеты, у маяка, у игрока.
   В запросе клиент присылает `baseVersion` — версию, которую он видел. Если сервер видит другую
   версию, операция отклоняется (`conflict`), и клиенту возвращается актуальный элемент — он
   «догоняет» сервер вместо того, чтобы затирать чужие изменения.
2. **Проверка предусловий.** Для перемещения проверяется, что клиент стартовал из той же клетки
   (`fx,fy`), что и сервер, что целевая клетка в границах, свободна от препятствия и от другого
   игрока (клетка маяка — исключение).
3. **Идемпотентность.** Каждая операция имеет `opId`. Повторная доставка той же операции (например,
   после разрыва соединения) не даёт двойного эффекта: opset хранит последние 1000 идентификаторов.
4. **Политика при конфликте.** Побеждает тот, чья операция пришла на сервер первой; проигравший
   не «зависает» — он получает актуальное состояние элемента и откатывается к нему.

Примеры из тестов:

* двое одновременно шагают в одну клетку → второй получает `conflict` «Клетку занял …» и остаётся на месте;
* двое берут одну монету → второй получает `conflict` «Монету уже забрал другой игрок», монета удаляется из его вида;
* двое одновременно захватывают маяк → второй получает `conflict` «Маяк уже захватил другой игрок» и новую версию маяка;
* клиент присылает `baseVersion`, устаревшую после чужой правки → `conflict` «Состояние монеты устарело».

## Восстановление после потери соединения (доп. 2)

* Клиент хранит последнее состояние в `localStorage` (`arena.cache`) и рисует его сразу при
  загрузке страницы, ещё до подключения к серверу.
* Каждое событие имеет номер `seq`; клиент помнит последний применённый номер и сохраняет его в токене
  сессии `arena.token`.
* При разрыве клиент показывает баннер, продолжает отображать сохранённое состояние и
  переподключается с экспоненциальной задержкой (0.5 с → 8 с). Ввод блокируется, чтобы не
  создавать конфликтующих операций; неподтверждённые операции остаются в очереди.
* После переподключения отправляется `resume {token, lastSeq}`. Если история событий на сервере
  покрывает разрыв, сервер досылает только пропущенные события (`replay`) — состояние сходится без
  полной пересылки мира. Если нет — приходит полный снапшот (`state`).
* Очередь неподтверждённых операций отправляется повторно; идемпотентность по `opId` гарантирует,
  что уже применённые операции не выполнятся дважды.
* Сервер отслеживает живость соединения через ping/pong heartbeat каждые 5 с: зависшие сокеты
  закрываются, остальные игроки получают событие `player` о том, что игрок ушёл в офлайн.

## Сохранение между запусками (требование 3)

* Состояние игры (`seq`, препятствия, монеты, маяк с владельцем и версией, игроки с очками и
  токенами) сериализуется в `data/game.json`.
* Запись выполняется с дебаунсом (300 мс) после изменений и принудительно при получении
  `SIGINT`/`SIGTERM` и в обработчике `exit`.
* Запись атомарная: данные пишутся в `game.json.tmp` и затем переименовываются, поэтому файл не
  может остаться частично записанным.
* При старте файл читается; при повреждении файла игра создаётся заново (сервер не падает).
* После перезапуска игрок с сохранённым токеном возвращается в игру со своими очками, а владелец
  маяка и монеты сохраняются (проверяется интеграционным тестом с реальным перезапуском процесса).

## Развёртывание (доп. 3)

### Локально

```bash
npm install
npm start
# ссылка: http://localhost:3000
```

Порт переопределяется переменной окружения `PORT`.

### Публичный хостинг

Приложение — обычный Node.js-сервер, ему нужен хостинг с поддержкой долгоживущих
WebSocket-соединений (Render, Railway, Fly.io, VPS/виртуальная машина, Docker).

**Render / Railway (без Docker):**

1. Залейте репозиторий на GitHub.
2. Создайте Web Service, build command — `npm install`, start command — `npm start`.
3. В переменных окружения при необходимости задайте `PORT` (иногда задаёт сам хостинг) и
   точку подключения `DATA_DIR` для постоянного диска.
4. После деплоя получите публичную ссылку вида `https://<имя>.onrender.com` — клиент
   автоматически переключится на `wss://` при загрузке по HTTPS.

**Docker:**

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
ENV PORT=3000
EXPOSE 3000
CMD ["npm", "start"]
```

```bash
docker build -t arena .
docker run -p 3000:3000 -v arena-data:/app/data arena
```

**VPS (nginx как реверс-прокси с поддержкой WebSocket):**

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
}
```

Важно: без постоянного диска состояние между перезапусками контейнера сохранится только внутри
контейнера. Чтобы данные не терялись, смонтируйте том на каталог `data` (переменная `DATA_DIR`).

## Использованные технологии

* Node.js 18+ (стандартные модули `http`, `fs`, `path`, `crypto`, `test`)
* `ws` — минимальная реализация серверного WebSocket (RFC 6455)
* HTML5 Canvas 2D, WebSocket API, `localStorage` — на клиенте
* Никаких UI-фреймворков и шаблонизаторов
